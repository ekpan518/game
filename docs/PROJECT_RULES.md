# 项目规则

## 技术边界

- 目标引擎固定为 Godot 4.7.2 stable，保留 GL Compatibility、Windows `d3d12` 与 Jolt Physics 配置。
- 运行时代码只使用 GDScript；代码标识符使用英文，玩家可见文案和交付文档使用中文。
- 只使用 Godot 内置节点、Mesh、材质、信号与 Tween，不依赖第三方插件、外部素材、原生扩展或 C#。
- 不实现网络联机、在线服务或遥测，不在项目中跟踪 `addons/`、`.godot/` 缓存或生成的 `.uid` 文件。
- 第一版只包含一名玩家、三辆 AI、一块无护栏圆形平台和一命制淘汰赛，不顺手扩展未来功能。

## 职责分离

- `DriverController`、`HumanDriver` 与 `AIDriver` 只产生标准化油门和转向命令，不能直接修改车辆位置、速度、击退或比赛结果。
- `BumperCar` 只负责车辆运动、快照、接触上报、击退应用、淘汰表现和强化表现；它不能决定击杀归属、胜负或重新开始。
- `BumperRules` 只做无场景依赖的冲量与倍率计算，不保存比赛状态。
- `MatchState` 保存稳定车辆编号、存活、最后攻击者、强化和批量淘汰结果。
- `MatchController` 是接触去重、击杀归属、死亡、强化、胜负与重新开始接受状态的唯一权威；车辆接触只能通过 `register_car()` 建立连接。
- `DeathZone` 只报告车辆进入，不能直接淘汰车辆；HUD 只显示控制器信号并发送重新开始请求，不能自行推断胜负。
- `BumperArena` 只负责装配和单向信号连接；只有该根脚本可以调用当前场景重载。

## 确定性与安全

- 四辆车使用稳定编号 1–4；无序车辆对按编号规范化，同帧只解析一次。
- 车辆接触使用对应物理帧的速度快照；缺失快照时丢弃该对，不能用过期数据猜测。
- 同帧接触先于批量死亡解析，玩家死亡优先于胜利，重复死亡和重复重新开始必须幂等。
- 击杀窗口使用比赛单调时间，不读取墙上时钟；AI 目标平局按较小稳定编号选择，不使用随机隐藏优势。
- 死亡后停止输入、运动和车辆碰撞；结果产生后冻结全部存活车辆。

## 验证纪律

- 新功能和修复遵循测试先行：先看到与缺失行为对应的 RED，再做最小实现并看到 GREEN。
- 新检出先运行 headless editor import，再运行原生 Godot 行为测试；原生测试是行为权威，PowerShell 验证器只辅助检查结构和仓库卫生。
- 有效与非法 scope 都必须验证；非法 scope 必须返回非零，不能因为脚本不可实例化而留下 headless 进程。
- 提交前必须检查 `git diff --check`、跟踪的缓存、`.uid`、`addons/` 和最终状态，只暂存任务明确列出的文件。
- 自动化通过不等于人工体验通过。未实际完成 F5、画面、输入、驾驶手感和真实碰撞检查时，文档与报告必须诚实标记为待人工验收。
